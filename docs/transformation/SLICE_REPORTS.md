## Slice 1 — Order exceptions and the unavailable-product workflow (PD-016) — local, 2026-10-31

### Built
- **Data (migration `1700007000000-OrderExceptions`, additive, reversible):** `order_exceptions`, `order_exception_items`, `order_exception_events`; `order_items.removed_at / removed_amount_minor / removal_exception_id` (the row, snapshots and amounts are never changed or deleted). One open `ITEM_UNAVAILABLE` case per order (partial unique index). Not applied anywhere except disposable test databases.
- **Workflow:** vendor (own part only; another branch gets the same 404 as a missing part) or Operations on its behalf marks items → customer notified once (`ORDER_ITEM_UNAVAILABLE`, English fallback in older apps) → the customer answers **continue without** or **cancel the order** → no answer changes nothing; the case waits in the Operations queue → Operations records what the customer said (PHONE/WHATSAPP + a note, both mandatory) and executes only that; an answer left in the app can be executed but never replaced. Cancelling runs the existing `AdminOrderExtrasService.cancel` (state machine, refunds, coupon restoration, PD-015 event) and needs `MANAGE_ORDER_ISSUES`; customer cancellation permissions are unchanged. **No substitution exists.**
- **Money (no new rule):** "continue without" reuses `applyOrderItemAmountDelta`, the rejected-part refund machinery (`OrderWalletRefundService.refundExcess`, `ManualTransferRefundService.reconcileReducedTotal`), the flash-sale release, and a smaller `amountDueMinor` for cash. Delivery fee untouched (PD-003); commission follows `segment.subtotalMinor`. Weight handling is untouched (C4; no approval step).
- **Isolated, not guessed** (the customer's answer is cleared, the case goes to Operations as HIGH priority with the reason): order would become empty; vendor part would become empty; an order-level discount/coupon on the part; unknown item amount; a second Manual-Transfer refund on a segment that already had one; order no longer editable. The whole case is all-or-nothing (savepoint).
- **Readers:** removed items disappear from the existing `items` arrays of the vendor, customer, admin and driver views (older apps never see them) and appear in a new `removedItems` array; inventory restore, the pickup weight gate, unpriced-custom-item gate, loyalty points, best-selling counters and the line-items report all ignore them. Stock and catalogue availability are never touched by marking or removing.
- **Admin API:** `GET admin/order-exceptions` (filters, paging), `…/summary`, `…/:id` (events), `POST admin/orders/segments/:id/unavailable-items`, `…/:id/record-decision`, `…/notes`, `…/escalate`, `…/assign`; events also appear in the merged order timeline. Vendor API: `POST vendor/orders/segments/:id/unavailable-items`. Customer API: `GET orders/:id/item-unavailability`, `POST …/:exceptionId/respond`.
- **UI:** dashboard `/exceptions` (queue, workload counts, case panel with decision/notes/escalate/assign, isolation reasons in English and Arabic; nav entry "Exceptions"); vendor order page control "An item is not available"; Customer app card with exactly two answers (confirmation before cancelling), removed-items section, localized notification, deep-link type.

## Slice 2 — Notification outbox, D-72 change detection, staff alerts, isolated-case visibility — local, 2026-10-31

Before starting, the working tree (including Slice 1) was archived and verified: `~/Downloads/hatly-backups/hatly-worktree-20261031-193916-after-slice1.tar.gz` (+ `.sha256` checked OK, gzip OK, 656 status lines); the earlier `…182035-full` archive is untouched.

### Built
- **Migration `1700007100000-NotificationOutboxAndChangeFeed` (additive, reversible; local/disposable DBs only — NOT applied in Production):** `customer_notifications.event_key`; `notification_outbox`; `staff_notifications`; `notification_preferences`; `change_events` + `change_feed_state` + 6 triggers; `order_exceptions.isolation_code/message/at`.
- **1 · Repeated cases.** A customer notification can now belong to an EVENT (`exception:<caseId>:items:<n>`). Unique per (order, type, event key); lifecycle notifications stay unique per (order, type). A second case on the same order notifies again; a retry/race of the same event writes once. Items added to a case the customer has not answered are folded into the notification already sent (unread, < 10 min old); a later separate addition notifies again.
- **2 · History.** Verified (e2e 126): a removed item keeps its row, name/price/quantity snapshots, link to its case, the case events, audit rows and the wallet refund; only the active `items` arrays change (`removedItems` keeps it). No row is deleted.
- **3 · Isolated cases in the queue.** `GET admin/order-exceptions` now returns `isolation {code,message,at}`, `responsible {userId,name}`, `requiredAction` (+ English text), filter `isolated=true`, KPI `isolated`; dashboard tab "Needs review", columns Responsible / Next step, case-panel banner "Nothing was changed on this order". A critical case (HIGH, ESCALATED or isolated) is never hidden because its order ended; `POST admin/order-exceptions/:id/resolve` (note required, only for an order that is over) closes it. No code path adjusts money for an isolated case: re-trying re-isolates (e2e 126 asserts totals, items, financial events and wallet rows unchanged).
- **4 · Outbox.** Written in the business transaction (rollback leaves nothing), idempotent on (event, recipient, channel), worker with `FOR UPDATE SKIP LOCKED` leases, exponential back-off, DEAD after max attempts, SKIPPED with a reason (NO_DEVICE, NO_VALID_DEVICE, PROVIDER_NOT_CONFIGURED, PREFERENCE_DISABLED). **There is no delivered/opened state anywhere (a DB CHECK forbids it): SENT = accepted by the provider.** In-app delivery is the inbox row and never depends on a provider. `GET admin/notification-outbox[/summary]` (VIEW_SYSTEM_HEALTH) shows states and which providers are configured. Delivery is at-least-once; every push carries `eventKey`.
- **5 · D-72.** `GET vendor/orders/changes` and `GET admin/changes?topics=orders,exceptions`: DB triggers write events in the same transaction; opaque cursor `v1.<txid>.<seq>` read in (txid, seq) order only for finished transactions (a bare sequence number loses late commits — proven in e2e 127); pagination (`limit`, `hasMore`); `reset:true` when the cursor is pruned/foreign; invalid cursor → 400; ids/kinds only, no customer data; vendors only see their own branches; ETag/304 works. Dashboard: the vendor order list and the Exceptions page reload on change instead of every 20 s; the old interval is the automatic fallback (unavailable endpoint, repeated errors), plus a 2-minute safety reload.
- **6 · Staff alerts.** Operations (ADMIN with MANAGE_ORDER_FULFILMENT; critical also MANAGE_ORDER_ISSUES, SUPER_ADMIN, the assignee) are alerted on a new case, assignment, escalation, "customer asked to cancel" and isolation; vendor staff of the part's branch on items removed, order cancelled, and "Operations ask you to act" (`POST admin/order-exceptions/:id/request-vendor-action`). The actor is never alerted about their own action. Inbox: `GET/POST staff/notifications…`, preferences `GET/PUT staff/notifications/preferences` (critical alerts cannot be muted in the inbox; push is optional and only for critical alerts to staff with a registered device). Dashboard: alerts bell in both shells with settings.
- **8 · Providers.** Nothing was configured. FCM is not configured in Production, so a push there would be recorded SKIPPED / PROVIDER_NOT_CONFIGURED; WhatsApp, SMS and e-mail have no provider and are never used.
